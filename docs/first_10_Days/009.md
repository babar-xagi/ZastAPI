# ZastAPI⚡ — Step 009: What Are Functions, Parameters, Arguments, and Return Values?

So far, our programs can hold values and calculate things:

```zig
const a: u32 = 10;
const b: u32 = 5;

const total: u32 = a + b;
```

But imagine our program needs to calculate the same kind of thing **100 times**.

We don't want to keep rewriting:

```zig
a + b
```

again and again.

We want to create a reusable little machine:

```text
give me two numbers
       ↓
     add them
       ↓
give me the answer
```

That little reusable machine is a:

# **Function** ⚙️

---

## 1. What is a function?

A beginner-friendly definition:

> **A function is a named group of instructions that performs a job.**

Imagine a machine:

```text
        ADD MACHINE

     ┌───────────────┐
  2 ─►               │
     │      ADD      ├──► 5
  3 ─►               │
     └───────────────┘
```

We give it:

```text
2
3
```

It does:

```text
2 + 3
```

and gives us:

```text
5
```

In Zig, that could look like:

```zig
fn add(a: u32, b: u32) u32 {
    return a + b;
}
```

Don't worry—we'll cut this into tiny pieces. 🔬

---

Imagine a machine called:

```text
makeJuice
```

You give it:

```text
orange
water
```

The machine performs some work:

```text
cut

```

and returns:


```text

  ↓

  ↓

  ↓
```

Programming functions work similarly.

```text
2
3
↓

```

# 3. Why do functions exist?

Without functions, imagine ZastAPI becoming:

```text
read request
parse request
find route
create response

read request
parse request
find route
create response

read request
parse request
find route
create response

...
```

Terrible. 😵

Instead, we can organize jobs:

```text
parseRequest()
findRoute()
createResponse()
startServer()
```

Now the code starts describing **what it is doing**.

That's one of the main reasons functions are so important.

# 7. What are the parentheses `()`?

After the function name:

```zig
fn add(...)
```

we have:

```text
(
)
```

Inside those parentheses, a function can declare what information it needs.

For example:

```zig
fn add(a: u32, b: u32)
```

Inside:

```text
a: u32
b: u32
```

These are called:

# **parameters**

---

# 8. What is a parameter?

A parameter is:

> A named input that a function expects to receive.

Our function:

```zig
fn add(a: u32, b: u32) u32 {
    return a + b;
}
```

expects two pieces of information:

```text
a
b
```

Both have type:

```text
u32
```

Think of two empty input boxes:

```text
        add()

┌────────────────────┐
│                    │
│ a: [ empty ]       │
│ b: [ empty ]       │
│                    │
└────────────────────┘
```

The function definition says:

> Whenever somebody uses me, give me an `a` and a `b`.

---

# 9. Parameter anatomy

Look at:

```zig
a: u32
```

You already know this pattern from Step 007.

```text
a     :     u32
│           │
name        type
```

So:

```zig
fn add(a: u32, b: u32)
```

means approximately:

```text
Function name: add

Needs:
a → u32
b → u32
```

# 10. Why do parameters need types?

Because Zig needs to know what kinds of values this function expects.

Imagine:

```zig
fn add(a: u32, b: u32)
```

We're saying:

> This function expects two `u32` values.

So something conceptually like:

```text
add(2, 3)
```

makes sense.

But passing completely unrelated data may not fit the function's contract.

This connects directly to Step 007:

```text
types
=
rules about what kind of values we're working with
```

# 11. What is an argument?

Now we reach a pair of words beginners often mix up:

```text
parameter
argument
```

Look at the function definition:

```zig
fn add(a: u32, b: u32) u32 {
    return a + b;
}
```

Here:

```text
a
b
```

are **parameters**.

Now suppose we use the function:

```zig
add(2, 3)
```

Here:

```text
2
3
```

are **arguments**.

So:

```text
PARAMETER
=
the input name in the function definition

ARGUMENT
=
the actual value you give when calling the function
```

# 14. What does it mean to "call" a function?

When we write:

```zig
add(10, 5)
```

we are **calling** the function.

Calling means:

> Ask the function to run its instructions.

Think of pressing a machine's START button:

```text
add
┌──────────────┐
│              │
│   START ▶    │
│              │
└──────────────┘
```

Writing:

```zig
add(10, 5)
```

is conceptually:

```text
Find function: add

Give it:
10
5

Run it
```

# 15. Function definition vs function call

These are different.

### Definition

```zig
fn add(a: u32, b: u32) u32 {
    return a + b;
}
```

This describes the machine.

Think:

```text
BUILD THE MACHINE
```

### Call

```zig
add(10, 5)
```

This uses the machine.

Think:

```text
RUN THE MACHINE
```

Mental model:

```text
Function definition
        ↓
"Here is how add works."

Function call
        ↓
"Run add now."
```

# 16. What is the function body?

Look:

```zig
fn add(a: u32, b: u32) u32 {
    return a + b;
}
```

The part inside:

```text
{
    ...
}
```

is the:

# **function body**

The body contains the function's instructions.

Here:

```zig
{
    return a + b;
}
```

The job is extremely simple:

```text
take a
take b
add them
return result
```

Later a ZastAPI function body may contain many instructions.

---

# 17. What are `{` and `}`?

These:

```text
{
}
```

are curly braces.

They group the function's body.

Conceptually:

```zig
fn add(...) {
```

means:

> The function's instructions begin here.

And:

```zig
}
```

means:

> The function's instructions end here.

Think of a room:

```text
add()
┌──────────────────┐
│                  │
│ function body    │
│ instructions     │
│                  │
└──────────────────┘
```

The braces are like the walls around that room.

# 18. What is a return value?

Our function:

```zig
fn add(a: u32, b: u32) u32 {
    return a + b;
}
```

calculates:

```text
a + b
```

But how does the answer come back to the code that called the function?

Through:

```zig
return
```

# 19. What does `return` mean?

`return` means approximately:

> Finish this function and send this value back to whoever called me.

Example:

```zig
return a + b;
```

Suppose:

```text
a = 10
b = 5
```

Then:

```text
a + b
=
15
```

So:

```zig
return 15;
```

sends:

```text
15
```

back.

Visual:

```text
          add(10, 5)

10 ─────►┌─────────────┐
         │             │
5 ──────►│   10 + 5    │
         │             │
         └──────┬──────┘
                │
              return
                │
                ▼
               15
```

# 20. What is the return type?

There are two `u32` parameter types:

```text

b: u32
```

Then after `)` we have another:


```text

```

# 27. Functions can call functions

Suppose:

```zig
fn add(a: u32, b: u32) u32 {
    return a + b;
}
```

And:

```zig
fn calculateScore() u32 {
    return add(10, 5);

```

Then:

```text
calculateScore()
       ↓

       ↓
      15
       ↓
returns 15
```

Programs become:

```text
function
  ↓
calls function
  ↓
calls another function
```

That's how large systems stay manageable.

# 36. Different calls, different arguments

Same function:

```zig
fn add(a: u32, b: u32) u32 {
    return a + b;
}
```

Call one:

```zig
add(2, 3)
```

produces:

```text
5
```

Call two:

```zig
add(10, 20)
```

produces:

```text
30
```

Call three:

```zig
add(100, 50)
```

produces:

```text
150
```

We wrote the addition logic only **once**.

That's:

# **reuse**

One of the biggest benefits of functions.

# 37. Functions help readability

Compare this:

```zig

```

with a larger real-world program containing hundreds of calculations and operations.

Eventually, giving jobs meaningful names lets us write code more like:

# 38. Functions help us hide complexity

This idea matters deeply for ZastAPI.

A ZastAPI developer might someday write:

```zig
app.get("/", home);
```

Simple.

But perhaps internally:

```text
app.get()
   ↓
validate path
   ↓
store handler
   ↓
build route metadata
   ↓
configure matcher
   ↓
update router
```

The developer doesn't need to see all of that every time.

The function:

```text
get()
```

provides a simple interface over complicated work.

This is one of the core ideas behind our entire framework.

# 43. And calling it


That's exactly why functions are powerful.
