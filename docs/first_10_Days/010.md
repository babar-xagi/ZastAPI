# ZastAPI⚡ — Step 010: What Are Scope, Local Variables, and Lifetime?

In Step 009, we created functions like:

```zig
fn add(a: u32, b: u32) u32 {
    return a + b;
}
```

Now a very important question appears:

> Where do `a` and `b` exist? Can another function see them? What happens to them after `add()` finishes?

That leads to three new ideas:

```text
Scope
Local variables
Lifetime
```

---

## 1. Start with a room analogy 🚪

Imagine a house:

```text
HOUSE
│
├── Kitchen
│   ├── spoon
│   └── cup
│
├── Bedroom
│   ├── pillow
│   └── lamp
│
└── Garage
    └── toolbox
```

A spoon belongs to the kitchen.

A pillow belongs to the bedroom.

If you're in the garage, you don't automatically have the kitchen spoon in your hand.

Programming has a similar idea:

> Names exist only in certain regions of code.

That region is called **scope**.

---

# 2. What is scope?

Beginner definition:

> **Scope is the region of code where a name can be used.**

Example:

```zig
fn demo() void {
    const number: u32 = 10;

    _ = number;
}
```

Here:

```text
number
```

exists inside the function body:

```text
{
    ...
}
```

So its scope is roughly:

```text
inside demo()
```

---

# 3. Visualize scope as a room

```text
demo()
┌────────────────────────────┐
│                            │
│ const number = 10;         │
│                            │
│ number can be used here ✅ │
│                            │
└────────────────────────────┘

Outside demo()

number ❌
```

Think:

```text
scope = visibility area
```

---

# 4. What is a local variable?

A variable declared inside a function is usually called a:

# **local variable**

Example:

```zig
fn calculate() u32 {
    const price: u32 = 10;
    const quantity: u32 = 3;

    return price * quantity;
}
```

Here:

```text
price
quantity
```

are local to:

```text
calculate()
```

So:

```text
calculate()
├── price
└── quantity
```

Another function does not automatically get those names.

---

# 5. Real-life analogy: your school locker 🎒

Imagine every student has their own locker.

Your locker contains:

```text
books
pen
notebook
```

Another student has another locker.

Their things do not magically become yours.

Functions work similarly.

```text
function A
┌────────────────┐
│ local variable │
└────────────────┘

function B
┌────────────────┐
│ different      │
│ local variable │
└────────────────┘
```

Each function has its own local names.

---

# 6. Parameters are local too

Remember Step 009:

```zig
fn add(a: u32, b: u32) u32 {
    return a + b;
}
```

Parameters:

```text
a
b
```

can be used inside:

```text
add()
```

So they behave like names local to that function call.

Mental picture:

```text
add()
┌────────────────────┐
│ a                  │
│ b                  │
│                    │
│ return a + b;      │
└────────────────────┘
```

Outside:

```text
a ❌
b ❌
```

---

# 7. Different functions can use the same local name

This is allowed conceptually:

```zig
fn first() void {
    const value: u32 = 10;
    _ = value;
}

fn second() void {
    const value: u32 = 20;
    _ = value;
}
```

There are two different:

```text
value
```

variables.

Think:

```text
first()
└── value = 10

second()
└── value = 20
```

They are in different scopes.

Like two houses can both have a room called:

```text
kitchen
```

without being the same kitchen.

---

# 8. Scope can exist inside smaller blocks

Functions are not the only scopes.

Curly-brace blocks can create nested regions too.

Conceptually:

```zig
fn demo() void {
    const outer: u32 = 10;

    {
        const inner: u32 = 20;

        _ = outer;
        _ = inner;
    }

    _ = outer;
}
```

Visual:

```text
demo()
┌─────────────────────────────┐
│ outer = 10                  │
│                             │
│   inner block               │
│   ┌─────────────────────┐   │
│   │ inner = 20          │   │
│   │                     │   │
│   │ outer ✅            │   │
│   │ inner ✅            │   │
│   └─────────────────────┘   │
│                             │
│ outer ✅                    │
│ inner ❌                    │
└─────────────────────────────┘
```

Very important.

---

# 9. Inner scopes can see outward

In our example:

```text
outer
```

was declared outside the inner block.

The inner block can use it:

```text
outer ✅
```

But the outer area cannot use:

```text
inner
```

after the inner block has ended.

Mental rule:

```text
inner can often see outward
outer cannot see inward
```

---

# 10. Scope is mostly about names

This distinction matters:

```text
scope
```

answers:

> Where can this name be referenced?

Now we introduce:

```text
lifetime
```

which answers a different question:

> How long does the underlying value/storage remain valid?

These ideas are related, but not identical.

---

# 11. What is lifetime? ⏳

Beginner definition:

> **Lifetime is how long a value or piece of storage remains valid during program execution.**

Imagine an ice cube. 🧊

```text
created
  ↓
exists for some time
  ↓
melts / disappears
```

That's like a lifetime.

For a local variable, a simple beginner mental model is:

```text
function starts
     ↓
local variable exists
     ↓
function works
     ↓
function ends
     ↓
local variable's local storage is no longer usable
```

---

# 12. Function call analogy: temporary workbench 🛠️

Imagine a worker enters a workshop.

They set up:

```text
hammer
screws
measurement notes
```

They do a job.

Then they clean the bench and leave.

A function call is similar:

```text
call function
   ↓
temporary local working state
   ↓
function finishes
   ↓
that local working state is finished
```

This is a very useful mental model.

---

# 13. Example

```zig
fn add(a: u32, b: u32) u32 {
    const result: u32 = a + b;

    return result;
}
```

During one call:

```zig
add(10, 5)
```

you can imagine:

```text
add() starts

a = 10
b = 5
result = 15

return 15

add() finishes
```

After that function call finishes, you should not imagine those exact local `a`, `b`, and `result` variables continuing as reusable locals somewhere forever.

---

# 14. But the returned value can continue

This is important.

```zig
const answer: u32 = add(10, 5);
```

Inside:

```text
result = 15
```

Then:

```text
return 15
```

The function finishes.

But:

```text
answer
```

in the caller now has:

```text
15
```

So:

```text
local result inside add()
        ↓
returns value 15
        ↓
caller stores it in answer
```

The local variable can disappear while the returned value is still available in another place.

---

# 15. Scope vs lifetime

Keep these separate:

```text
SCOPE
=
Where can the name be used?

LIFETIME
=
How long is the underlying value/storage valid?
```

Real-life analogy:

```text
Scope = which rooms your key opens 🔑

Lifetime = how long the building exists 🏠
```

Different questions.

---

# 16. Let's use a ZastAPI example 🌐

Imagine later:

```zig
fn home() []const u8 {
    const message = "Hello ZastAPI!";

    return message;
}
```

Inside:

```text
home()
┌─────────────────────────┐
│ message                 │
│                         │
│ return message          │

```

The name:

```text
message
```

is local to:

```text

```

Another route handler cannot simply write:

```text
message
```

and expect that local name to exist.

# 17. Another route gets its own locals

```zig
fn about() []const u8 {
    const message = "About ZastAPI";

    return message;

```

Now we have:

```text
home()
└── message = "Hello ZastAPI!"

about()
└── message = "About ZastAPI"
```

Same name.

Different local scopes.

No problem.

# 18. Why scope is useful

Imagine every variable in the whole program could be accessed and changed from everywhere.

😵

You might have:

```text
port
user
request
response
count
buffer
name
route
```

all visible everywhere.

Then one function could accidentally change something another function depends on.

Scope helps us keep code organized:

```text
function A
owns its local details

function B
owns its local details

function C
owns its local details
```

This reduces accidental interference.

---

# 19. Scope creates boundaries

Think:

```text
ZastAPI
│
├── parseRequest()
│   ├── method
│   ├── path
│   └── headers
│
├── findRoute()
│   ├── route
│   └── match
│
└── sendResponse()
    ├── body
    └── status
```

Each function can work with its own local data.

That is much easier to reason about than one giant shared mess.

# 20. What happens with repeated function calls?

Suppose:

```zig
fn add(a: u32, b: u32) u32 {
    const result: u32 = a + b;
    return result;
}
```

First call:

```zig
add(2, 3)
```

Conceptually:

```text
a = 2
b = 3
result = 5
```

Then function ends.

Second call:

```zig
add(100, 50)
```

Conceptually:

```text
a = 100
b = 50
result = 150
```

Each call has its own working values.

This is extremely important for server software later.

Later ZastAPI might handle:

```text
Request A
GET /users/1

```

Each handler invocation needs its own request-specific data.

Conceptually:

```text
handler call A
┌───────────────────┐

┌───────────────────┐
```

# 22. Where do local variables physically live?

You may hear:

```text
stack
```

and assume:

> All local variables are always literally on the stack.

That is a useful beginner approximation, but not always literally true.

The compiler can sometimes:

```text
use CPU registers
optimize a value away
store data differently
```

So the safer beginner statement is:

> Local variables belong to a function/block logically; the compiler decides their exact physical representation.

We'll learn the stack properly later.

---

# 23. Scope does not mean storage location

Very important:

```text
scope
```

is a **language visibility concept**.

It is not:

```text
RAM address
```

or:

```text
stack location
```

For example:

```text
scope
=
where name can be referenced
```

whereas:

```text
memory
=
where data is represented during execution
```

Don't mix them.

# 25. Why `_ = value;` appears in examples

You may see:

```zig
_ = x;
```

Zig is strict about unused local values.

For now, think:

```text
_ = x;
```

means roughly:

> I know `x` exists; intentionally ignore/use it here.

We'll properly learn:

```text
_
```

later.

Don't focus on it yet.

# 26. Lifetime and references — tiny preview 🚧

Later Zig will let us work with:

```text
pointers
slices
references to memory
```

Then lifetime becomes much more serious.

Imagine:

```text
function creates temporary local data
      ↓
returns a pointer to that temporary storage
      ↓
function ends
      ↓
storage is no longer valid
```

That can be dangerous.

Zig makes memory validity explicit, so we'll spend a lot of time on this later.

For now:

```text
don't return references to temporary local storage
```

is a useful preview, but don't try to implement pointer code yet.

# 29. Shadowing — do not use yet

Some languages allow a local name to hide another name with the same spelling in a nested scope.

This concept is called:

```text
shadowing
```

Zig has rules around name collisions/shadowing, but we are not going there yet.

For learning ZastAPI, we'll prefer very clear names and avoid intentionally confusing reuse.

# 30. Scope with function parameters

Let's dissect:

```zig
fn multiply(a: u32, b: u32) u32 {
    const result: u32 = a * b;

    return result;
}
```

Inside:

```text
a
b
result
```

are visible.

Outside:

```text
a ❌
b ❌
result ❌
```

But this:

```zig
const answer: u32 = multiply(4, 5);
```

creates a different local:

```text
answer
```

in the caller's scope.

# 33. Why lifetime matters for web servers

Servers may run for:

```text
minutes
hours
days
months
```

but individual request data may only be needed for:

```text
milliseconds
```

Conceptually:

```text
ZastAPI server lifetime
────────────────────────────────────────────>

Request A
   ├─────┤

Request B
          ├──────┤

Request C
                    ├───┤
```

The server lives a long time.

Each request's temporary data may live only briefly.

This will become important when we design:

```text

```

# 34. Scope and lifetime are not always identical

This is advanced, but worth planting one seed.

A name might stop being accessible because its scope ended, while some copied or separately allocated data may continue elsewhere.

So don't memorize:

```text
scope = lifetime
```

They are related, but different.

Use:

```text
scope
→ visibility

lifetime
→ validity duration
```

# 39. Key vocabulary

| Concept                 | Beginner meaning                             |
| ----------------------- | -------------------------------------------- |
| **Scope**               | Region where a name can be used              |
| **Local variable**      | Variable declared inside a function/block    |
| **Parameter scope**     | Parameters can be used inside their function |
| **Nested scope**        | Scope inside another scope                   |
| **Lifetime**            | How long data/storage remains valid          |
| **Function invocation** | One execution/call of a function             |
| **File/module scope**   | Broader scope outside individual functions   |
