# 2. First concept: what is a directory? 📁

A **directory** is another word for a folder.

For example:

```text
ZastAPI/
```

is a directory.

Inside it we have:

```text
src/
```

which is another directory.

Think about a school bag 🎒:

```text
School Bag
│
├── Math notebook
├── Pencil
└── Books folder
```

A programming project is similar:

```text
ZastAPI
│
├── build.zig
├── build.zig.zon
└── src
```

The folder helps us organize things.

---

# 3. What does `src` mean?

`src` is short for:

```text
source
```

And **source code** means:

> The instructions we humans write for the computer.

So:

```text
src/
```

basically means:

```text
source-code/
```

Developers use `src` because it's shorter.

Our Zig code lives here:

```text
src/
├── main.zig
└── root.zig
```

---

# 4. What is a file? 📄

A file is a named piece of information stored on your computer.

You already know files such as:

```text
photo.jpg
movie.mp4
notes.txt
```

Programming also uses files:

```text
main.zig
```

The important part is:

```text
.zig
```

That tells us:

> This is a Zig source-code file.

Similar examples:

```text
hello.py     → Python
app.kt       → Kotlin
index.ts     → TypeScript
main.zig     → Zig
```

So:

```text
main.zig
```

means approximately:

> A file named `main` containing Zig code.

# 5. What is `main.zig`?

Open:

```text
src/main.zig
```

You can use VS Code, Zed, Notepad++, or whatever editor you're using.

Don't worry about understanding the code yet.

For now we only care about its job.

Think of:

```text
main.zig
```

as the **front door 🚪 of the program**.

When we eventually run our program:

```powershell
zig build run
```

execution begins from the program's entry point associated with our executable.

Later we'll understand things like:

```zig
pub fn main()
```

But **not yet**.

For Step 001:

```text
main.zig
      │
      ▼
starting area of our executable
```

That's enough.

---

# 6. Then what is `root.zig`?

This one can feel confusing at first.

Think about ZastAPI eventually being something another Zig program can use:

```zig
const zast = @import("zast");
```

We need a place representing the main public library/module.

That's what `root.zig` can serve as.

Very roughly:

```text
main.zig
   │
   └── executable/program

root.zig
   │
   └── reusable Zast library
```

Later our `root.zig` could eventually expose things like:

```zig
pub const App = ...;
pub const Router = ...;
pub const Request = ...;
```

Then developers could use:

```zig
const zast = @import("zast");

var app = zast.App.init();
```

But that's far in the future.

Today just remember:

```text
main.zig  → program side
root.zig  → library side
```

---

# 7. What is `build.zig`? 🏗️

Now look at:

```text
build.zig
```

Don't try to understand its code.

Its purpose is more important first.

Imagine we're building a house 🏠.

We have:

```text
bricks
wood
doors
windows
```

Someone needs instructions saying:

```text
Use these materials.
Build this part.
Put the result here.
```

Software has a similar process.

Our source code:

```text
src/main.zig
```

has to become something the computer can execute.

`build.zig` contains instructions describing how Zig should build the project.

Very simplified:

```text
src/main.zig
      │
      ▼
  build.zig
      │
      ▼
 Zig compiler
      │
      ▼
 executable program
```

So for now:

```text
build.zig = project build instructions
```

---

# 8. What is `build.zig.zon`?

Another weird name. 😄

```text
build.zig.zon
```

`.zon` means:

```text
Zig Object Notation
```

It's used for project/package metadata and dependencies.

Think of it like the project's information card 🪪.

It can describe things such as:

```text
project/package name
version
dependencies
paths belonging to the package
```

Later, imagine ZastAPI uses another Zig package:

```text
ZastAPI
    │
    └── dependency XYZ
```

Information about dependencies can be represented through this package configuration.

But ZastAPI's goal may eventually be very dependency-light or even zero-third-party in core areas.

Still, Zig's package system needs its project metadata.

For now:

```text
build.zig.zon
=
package information
```

Don't edit it today.

# 10. First experiment 🔬

We're going to do something extremely simple.

Run:

```powershell
zig build
```

Don't worry about what building means deeply yet.

We only want to ask Zig:

> Can you understand and build the project that `zig init` created?

If everything is correct, the command should finish successfully.

Then run:

```powershell
zig build test
```

Again, don't worry about tests yet.

We're only checking that our starting project works.

Finally:

```powershell
zig build run
```

You may see output from the default Zig starter program.

Whatever exact default message your Zig version generated is okay.

# 11. One new word: command

You just typed:

```powershell
zig build
```

This is a **command**.

Think of a command as telling the computer:

> Do something.

For example:

```powershell
zig version
```

means approximately:

> Zig, tell me your version.

And:

```powershell
zig build
```

means approximately:

> Zig, build this project according to its build configuration.

We'll later learn:

```text
terminal
shell
PowerShell
command
argument
program
process
```

one at a time.
