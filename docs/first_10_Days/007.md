# ZastAPI⚡ — Step 007: What Are Values, Types, `const`, and `var` in Zig?

Now we finally start understanding **real Zig code character by character**. ⚡

Consider this:

```zig
const port: u16 = 8000;
```

By the end of Step 007, this line should no longer look mysterious.

The current Zig language reference defines `const` as declaring something that cannot be modified, while `var` declares something that may be modified. Zig also recommends preferring `const` when mutation isn't needed. ([Zig Programming Language][1])

---

## 1. First: what is a value?

A **value** is actual information your program works with.

For example:

```text
8000
```

is a value.

```text
42
```

is a value.

```text
true
```

is a value.

```text
"ZastAPI"
```

is also a value.

Think of groceries inside labeled containers:

```text
┌─────────────┐
│    8000     │
└─────────────┘

┌─────────────┐
│  "ZastAPI"  │
└─────────────┘

┌─────────────┐
│    true     │
└─────────────┘
```

The things **inside** are the values.

So the simplest definition is:

> **Value = actual piece of data.**

```text
┌─────────────────────┐

│                     │
│ value: 8000         │

```

There are two different ideas here.

```text

```

# 3. Name and value are not the same

This distinction matters.

Consider:

```zig
const port = 8000;
```

We have:

```text
name
 ↓
port
```

and:

```text
value
 ↓
8000
```

When we later write:

```text
port
```

our code can refer to that value using its meaningful name.

Instead of seeing this everywhere:

```text
8000
8000
8000
8000
```

we can write:

```text
port
```

Much easier for humans. 🧠

# 4. Now what is a type?

Here's the next big concept.

Imagine four boxes:

```text
42

"ZastAPI"

true

3.14
```

Those values are not all the same kind of thing.

`42` is a whole number.

`true` represents true/false information.

`"ZastAPI"` is text.

`3.14` represents a number with a fractional part.

Programming languages need to know these differences.

That's where **types** come in.

> **Type = a description/category of what kind of value something is.**

---

# 5. Real-life analogy: containers 🧃

Imagine a kitchen.

You have:

```text
Water bottle
Egg carton
Sugar jar
Fruit basket
```

They're all containers, but they're designed for different things.

You wouldn't normally put:

```text
water
```

into an egg carton. 😄

Types work similarly.

```text
Number container
└── 8000

Boolean container
└── true

Text-like value
└── "ZastAPI"
```

A type helps Zig know what kind of data it's dealing with and what operations make sense.

---

# 6. Why does Zig care about types?

Suppose we have:

```text
8000
```

We can perform numerical operations:

```text
8000 + 1
```

But imagine asking:

```text
"ZastAPI" + 1
```

What should that mean?

Text and numbers behave differently.

Types help the compiler understand things like:

```text
what kind of data is this?

how should it be represented?

what operations are legal?

how much space may be needed?

can this value be used here?
```

This is part of Zig's **type system**.

We'll learn that slowly.

# 7. Our first Zig integer type: `u16`

Let's expand our code:

```zig
const port: u16 = 8000;
```

Focus on:

```zig
u16
```

Break it apart:

```text
u   16
│    │
│    └── 16 bits
│
└── unsigned
```

`unsigned` means:

> No negative numbers.

So a `u16` can represent whole numbers from:

```text
0
```

through:

```text
65535
```

Our port value:

```text
8000
```

fits comfortably inside that range.

So:

```zig
const port: u16 = 8000;
```

means approximately:

> Create something named `port`, whose type is `u16`, and give it the value `8000`.

---

# 8. Signed vs unsigned — tiny preview

Imagine:

```text
temperature = -5
```

That needs negative numbers.

An unsigned integer wouldn't fit that job.

Later we'll encounter names such as:

```text
u8
u16
u32
u64
```

and:

```text
i8
i16
i32
i64
```

The rough idea is:

```text
u → unsigned → 0 and positive values

i → signed integer → negative, zero, positive
```

Don't memorize all of them yet.

For ZastAPI, you'll naturally meet them as the project grows.

# 9. Now let's dissect the entire line 🔬

Here it is:

```zig
const port: u16 = 8000;
```

Let's cut it into pieces:

```text
const   port   :   u16   =   8000   ;
```

And understand them one at a time.

---

## `const`

```zig
const
```

This is a Zig **keyword**.

It tells Zig we're declaring a name whose value cannot simply be reassigned later.

For our beginner mental model:

```text
const
=
this association stays fixed
```

So:

```zig
const port: u16 = 8000;
```

doesn't allow us to later do:

```zig
port = 9000;
```

The compiler would reject assigning a new value to that `const`. ([Zig Programming Language][2])

---

## `port`

Next:

```zig
port
```

That's the name we chose.

Programming calls a name like this an:

# **identifier**

An identifier identifies something in our code.

Examples might eventually be:

```text
port
name
request_count
server
router
user
```

For now:

```text
identifier
=
a name we use in code
```

---

# 10. What does `:` mean?

Now:

```zig
:
```

In this declaration, the colon separates the identifier from its explicitly written type:

```zig
port: u16
```

Read it approximately as:

> `port` has type `u16`.

Mental picture:

```text
port : u16
 │     │
name   type
```

---

# 11. What does `=` mean?

Next:

```zig
=
```

Here it connects the declaration to its initial value.

```zig
port: u16 = 8000
```

Think:

```text
port
gets its initial value
8000
```

For now, you can read:

```text
=
```

as:

> give/assign this value.

We'll learn assignment more carefully later.

---

# 12. `8000`

Then:

```zig
8000
```

That's the actual value.

More specifically, because we've literally written the number into our source code, this is an example of a:

# **literal**

A literal is a value written directly in the code.

Examples:

```zig
8000
42
true
"ZastAPI"
```

These are all literals.

So:

```text
8000
=
integer literal
```

# 13. Finally `;`

At the end:

```zig
;
```

This is a semicolon.

For now, think:

> This marks the end of this declaration/statement.

So visually:

```zig
const port: u16 = 8000;
                       ↑
                       end
```

You'll see `;` everywhere in Zig.

# 15. Now what is `var`?

Consider something that needs to change.

A server might count requests.

At first:

```text
0 requests
```

Then:

```text
1 request
```

Then:

```text
2 requests
```

Then:

```text
3 requests
```

That value changes while the program runs.

In Zig we can use:

```zig
var requests: u32 = 0;

requests += 1;
```

Zig's language reference defines `var` for a variable whose value may be modified. ([Zig Programming Language][2])

---

# 16. Real-life analogy: whiteboard vs printed sign

Imagine two things.

A printed sign:

```text
PORT
8000
```

We don't intend to change it.

Think:

```zig
const port: u16 = 8000;
```

Now imagine a whiteboard:

```text
REQUESTS

0
```

Someone updates it:

```text
1
```

then:

```text
2
```

then:

```text
3
```

Think:

```zig
var requests: u32 = 0;
```

So:

```text
const → don't reassign it

var → value may change
```

# 17. Why Zig prefers `const`

Suppose something does not need to change.

We could imagine writing mutable state everywhere, but then a programmer has to wonder:

```text
Will this change?

Who changes it?

When does it change?

What value does it have now?
```

When something is `const`, the reader knows:

```text
this name won't be reassigned
```

That's simpler to reason about.

The official Zig documentation explicitly recommends preferring `const` over `var` when mutation isn't required. ([Zig Programming Language][1])

That's a useful ZastAPI rule from day one:

```text
Use const by default.
Use var when something genuinely needs to change.
```

# 19. What is mutation?

New word:

# **mutation**

Mutation simply means:

> Changing a value/state after it was created.

For example:

```zig
var score: u32 = 10;
score = 20;
```

Conceptually:

```text
score
 │
 ▼
10
```

becomes:

```text
score
 │
 ▼
20
```

That's mutation.

---

# 20. `const` does NOT mean "magic permanent data forever"

This distinction will save you confusion later.

For our beginner model:

```text
const = can't reassign this variable
```

That's much better than thinking:

```text
const = this thing can never change anywhere in the universe
```

Pointers, referenced data, containers, and compile-time behavior introduce more nuance later. Zig's documentation specifically notes that pointers have their own constness rules. ([Zig Programming Language][2])

We don't need those details yet.

Just remember:

```text
const name
=
you cannot simply assign a different value
to that declaration later
```

# 22. But sometimes Zig can infer types 🧠

You may also see:

```zig
const port = 8000;
```

We didn't explicitly write:

```zig
: u16
```

Zig can often determine an appropriate type from context or retain a compile-time-known literal type until the value needs to fit somewhere specific.

This is called:

# **type inference**

The compiler is doing some work for us.

Conceptually:

```text
const port = 8000;
             │
             ▼
compiler knows information
about this value
```

For now, though, while learning types, we'll often write explicit types when they help us see what's happening.

---

# 23. Important: don't assume inferred integer literals are automatically `u16`

This is a subtle Zig-specific detail.

If we write:

```zig
const port = 8000;
```

don't mentally translate that immediately into:

```text
port is definitely u16
```

Zig has special compile-time literal types and coercion rules.

We'll learn those much later.

For now:

```text
const port: u16 = 8000;
```

is better for learning because the intended type is visible.

# 26. Types also affect memory

Remember Step 006?

```text
variables
↓
data
↓
memory
```

Types help the compiler know how data should be represented.

For example:

```zig
const port: u16 = 8000;
```

`u16` tells us the integer representation uses:

```text
16 bits
```

And from Step 005:

```text
8 bits = 1 byte
```

Therefore:

```text
16 bits
=
2 bytes
```

So a plain `u16` represents its integer value using two bytes.

🔥 Step 005 and Step 007 just connected.

# 28. What values are allowed in `u16`?

Since a `u16` has:

```text
16 binary bits
```

there are:

```text
2^16
```

possible bit patterns.

That's:

```text
65,536
```

different possibilities.

Starting from zero gives:

```text
0 → 65,535
```

So:

```zig
const port: u16 = 8000;
```

works.

But something like:

```zig
const number: u16 = 100000;
```

doesn't fit into a `u16`.

The compiler can catch that kind of mismatch.

This is another example of types helping us.

# 29. Types are like contracts 🤝

Imagine:

```zig

```

We told Zig:

> `port` should contain a value valid for `u16`.

Then Zig can help enforce that agreement.

Conceptually:

```text
YOU
 │
 │ promise
 ▼
port is u16
 │
 ▼
COMPILER
 │
 │ checks
 ▼
Does 8000 fit?
 │
 ├── yes → continue
 └── no  → error
```

That's one big reason strong types are useful.

# 38. We can deliberately ask the compiler to protect us

After the first experiment works, temporarily add:

```zig
port = 9000;
```

So conceptually you'd have:

```zig
const port: u16 = 8000;

port = 9000;
```

Try compiling/running it.

Zig should reject the reassignment because `port` was declared `const`. This behavior is documented directly in Zig's language reference. ([Zig Programming Language][2])

That compiler error is useful.

It's saying:

> You told me this was constant, and now you're trying to change it.

After seeing the error, remove:

```zig
port = 9000;
```

and return the experiment to working code.
