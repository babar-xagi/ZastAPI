# **Compiler** 🧠⚙️

A compiler is one of the most important ideas in programming.

---

## 1. The simplest meaning

A compiler is a program that takes code written in a programming language and turns it into something the computer can execute.

For us:

```text
Zig source code
      ↓
Zig compiler
      ↓
Executable / machine instructions
```

So when we write:

```zig
const age = 15;
```

the CPU does **not** directly read:

```text
const
age
=
15
```

The Zig compiler processes that code first.

---

# 2. Real-life analogy: translator 🌍

Imagine three people:

```text
You
↓
Translator
↓
Person who speaks another language
```

You speak Urdu.

Another person only understands Japanese.

Without a translator:

```text
You ─────X─────> Other person
```

Communication fails.

With a translator:

```text
You
 │ Urdu
 ▼
Translator
 │ Japanese
 ▼
Other person
```

Programming is similar:

```text
You
 │ Zig code
 ▼
Zig compiler
 │ machine instructions
 ▼
CPU
```

So the compiler is like a translator between:

```text
human-friendly programming code
```

and

```text
machine-friendly instructions
```

This analogy is not perfect, but it gives us the right mental picture.

---

# 3. But the compiler does more than translate

A compiler is also a **checker**. 🔍

Imagine you write:

```zig
const age = 15;
```

The compiler can understand the structure.

But suppose you write:

```zig
const age 15;
```

Now something is missing:

```text
=
```

The compiler may stop and report an error.

So the compiler has at least two big jobs in our beginner mental model:

```text
1. Check the code
2. Translate/build the code
```

Think:

```text
Your code
   ↓
Compiler checks it
   ↓
Is it valid?
   │
   ├── NO → error
   │
   └── YES
         ↓
      create machine-ready output
```

---

# 4. Real-life analogy: airport security ✈️

Imagine you're going through an airport.

Before getting on the plane:

```text
You
 ↓
Security check
 ↓
Valid?
 ↓
Board plane
```

If there is a problem:

```text
Security stops you
```

A compiler does something conceptually similar.

Your code goes in:

```text
source code
```

The compiler checks:

```text
Is the syntax valid?
Do the names make sense?
Do the types make sense?
Can this code be built?
```

If not:

```text
compiler error
```

If yes:

```text
continue building
```

---

# 5. Compiler errors are useful

This is important.

When the compiler says:

```text
error
```

that does **not** mean:

> You failed.

It means:

> Something in the code needs fixing before I can continue.

Imagine a teacher checking:

```text
2 + ? = 5
```

and saying:

```text
Something is missing.
```

The compiler is giving you information.

Later, learning how to read errors will become one of your strongest programming skills.

---

# 6. What does the compiler produce?

Eventually, the compiler can help produce an:

```text
executable
```

An executable is a program file your operating system can run.

Think:

```text
main.zig
   │
   │ compiler
   ▼
executable
   │
   │ run
   ▼
program starts
```

On Windows, executables often look like:

```text
something.exe
```

So someday ZastAPI might help us produce something like:

```text
school-server.exe
```

Conceptually:

```text
school server Zig code
        ↓
Zig compiler
        ↓
school-server.exe
        ↓
run
        ↓
server starts
```

---

# 7. Source code is not the executable

This distinction is very important.

This:

```text
src/main.zig
```

is:

```text
source code
```

This is not yet the same thing as:

```text
running application
```

Think about a recipe again. 🍕

```text
Recipe
≠
Pizza
```

Similarly:

```text
main.zig
≠
running program
```

We need a process in between:

```text
source code
    ↓
compiler/build process
    ↓
executable
    ↓
run
```

---

# 8. What happens when we use `zig build`?

You already ran:

```powershell
zig build
```

Very roughly, you were saying:

> Zig, follow this project's build instructions and build the project.

Remember:

```text
build.zig
```

contains our build logic.

So conceptually:

```text
zig build
   │
   ▼
read build instructions
   │
   ▼
find our Zig source code
   │
   ▼
compiler processes code
   │
   ▼
produce build output
```

There are more details internally, but **do not learn those yet**.

This mental model is enough.

---

# 9. `zig build run`

Now this command becomes easier:

```powershell
zig build run
```

We can mentally split it:

```text
build
+
run
```

Meaning approximately:

```text
Build the program
      ↓
Then run it
```

So:

```text
main.zig
   ↓
compiler/build
   ↓
executable
   ↓
run
   ↓
main()
```

Nice. ⚡

# 10. What happens inside the compiler?

At a beginner level, imagine several checkpoints.

```text
Your Zig code
     ↓
Read the code
     ↓
Check syntax
     ↓
Understand meaning
     ↓
Check types/rules
     ↓
Generate machine-oriented code
     ↓
Create final program
```

We will eventually learn words such as:

```text
parsing
AST
semantic analysis
types
IR
machine code
linking
```

But not now.

Those are future lessons.

For now, compress all of that into:

```text
compiler
=
check + understand + translate
```

---

# 11. Another analogy: factory 🏭

Imagine:

```text
Raw material
   ↓
Factory
   ↓
Finished product
```

For programming:

```text
Zig source code
    ↓
Compiler
    ↓
Executable
```

Our code is the raw material.

The compiler is the factory.

The executable is the finished product.

But the factory also has quality control.

If raw material is wrong:

```text
STOP
```

That's like a compiler error.

---

# 12. What is machine code?

We're only touching this lightly.

The CPU needs very low-level instructions.

You may imagine:

```text
10110100
01001010
11000101
```

But real machine instructions are more complicated than simply "binary text."

The important concept is:

```text
Zig code
```

is meant for humans.

```text
Machine instructions
```

are meant for the processor.

The compiler connects those worlds.

---

# 13. CPU and compiler are different

Do not mix these two.

The:

```text
compiler
```

creates/processes the program.

The:

```text
CPU
```

executes machine instructions.

Think:

```text
Architect
      ↓
creates a building plan

Worker
      ↓
uses the plan and builds
```

Very roughly:

```text
Compiler
      ↓
creates executable instructions

CPU
      ↓
executes those instructions
```

Different jobs.

---

# 14. Compile time vs run time

This is our first introduction to two very important terms.

## Compile time

When the compiler is processing your code.

```text
source code
   ↓
compiler working
```

That's:

```text
compile time
```

## Run time

When the finished program is actually running.

```text
executable
   ↓
CPU executing
```

That's:

```text
runtime
```

Simple example:

```text
Compile time:
"Can this program be built?"

Run time:
"The built program is now doing its job."
```

We'll spend much more time on this later because Zig makes compile-time programming especially interesting.

# 15. ZastAPI⚡ example

Much later, imagine a developer writes:

```zig
const zast = @import("zast");

pub fn main() !void {
    var app = try zast.App.init();

    app.get("/", home);

    try app.run();
}
```

The developer sees nice, simple Zig code.

But behind that simplicity:

```text
Developer code
      ↓
ZastAPI library
      ↓
Zig compiler
      ↓
machine instructions
      ↓
CPU
      ↓
HTTP server runs
```

This matters for our ZastAPI goal.

We want developers to write simple code:

```zig
app.get("/", home);
```

while Zig and ZastAPI handle a lot of difficult work underneath.

```text
             YOU

        └──────┬───────┘
```

---

# 17. Five words to remember

* **Compiler** → checks/processes source code and helps turn it into machine-executable output.
* **Compile** → process source code with the compiler.
* **Executable** → program file that can be run.
* **Compile time** → when your code is being compiled.
* **Runtime** → when your finished program is actually running.

You do **not** need to memorize them perfectly yet.

We'll use them hundreds of times while building ZastAPI.
