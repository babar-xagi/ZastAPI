# ZastAPI⚡ — Step 003: What Is a Programming Language?

In Step 002 we learned:

```text
Program = instructions for a computer
```

Now the next question is:

> If a program is just instructions, why can’t we simply write normal English and let the computer understand it?

Because computers do not naturally understand human language the way we do.

That is why we use a **programming language**. 🧠⚡

---

## 1. Real-life analogy: two people with different languages

Imagine:

```text
You speak Urdu
Another person speaks Japanese
```

You say:

```text
Bring me water
```

But the other person does not understand Urdu.

The problem is not the instruction.

The problem is:

```text
language mismatch
```

You need a language both sides can understand, or a translator between them.

Programming works similarly.

You write:

```zig
const name = "ZastAPI";
```

But the CPU does not directly understand:

```text
const
name
=
"ZastAPI"
```

Those words are for **humans**.

---

# 2. What is a programming language?

A programming language is:

> A special language humans use to write instructions for computers.

Examples:

```text
Python
Kotlin
TypeScript
Zig
C
Rust
Java
```

For our project, we selected:

```text
Zig
```

So we will write ZastAPI in Zig.

---

# 3. Why not use normal English?

Suppose you told a computer:

```text
Please create a server.
```

Humans understand this sentence.

But many questions appear:

```text
Which port?
Which network?
What should happen when a request arrives?
How much memory should be used?
What exactly does "server" mean?
```

Human language can be vague.

Programming languages are much more strict.

For example:

```zig
const port = 8000;
```

This is very specific.

We are saying:

```text
create something called port
give it the value 8000
```

The syntax has rules.

---

# 4. What is syntax?

New word:

# **Syntax**

Syntax means:

> The rules for writing a language correctly.

English has rules:

```text
I am learning Zig.
```

This makes sense.

Something like:

```text
Learning am Zig I.
```

uses the same words, but the structure is wrong.

Programming languages also have structure.

For example, Zig may accept:

```zig
const age = 15;
```

but not something random like:

```zig
age const 15 =
```

because that breaks Zig's syntax rules.

So:

```text
Programming language
        │
        └── has syntax
```

---

# 5. Zig is a language for humans and tools

When you write:

```zig
pub fn main() void {
}
```

you can eventually learn what every piece means.

The computer's CPU cannot directly execute that text.

So there is another step:

```text
Zig source code
      ↓
something translates/processes it
      ↓
machine instructions
```

That "something" is where the **compiler** comes in.

We will focus heavily on the compiler next.

---

# 6. What does the computer actually understand?

At a very low level, a CPU executes **machine instructions**.

These are not friendly source-code words like:

```zig
const
fn
if
while
```

They are encoded in a form the processor understands.

You can think of the levels like this:

```text
YOU
 │
 │ write
 ▼
Zig code
 │
 │ much easier for humans
 ▼
Compiler
 │
 │ translates
 ▼
Machine instructions
 │
 │ CPU understands
 ▼
CPU
```

Do not worry about actual binary yet.

We'll reach that slowly.

# 7. Real-life analogy: restaurant waiter 🍽️

Imagine:

```text
You
↓
Waiter
↓
Kitchen
```

You say:

```text
I want one pizza.
```

The kitchen has its own process:

```text
prepare dough
add sauce
add cheese
bake
```

You don't walk into the kitchen and control every oven yourself.

The waiter helps connect your request to the kitchen process.

A compiler is not exactly a waiter, but the analogy helps:

```text
Human-friendly Zig code
          ↓
       Compiler
          ↓
Machine-friendly instructions
```

The compiler bridges the gap.

# 8. Why do programming languages differ?

You might ask:

> If all programs eventually reach machine instructions, why do we have Python, Zig, Kotlin, Rust, etc.?

Because each language is designed with different goals.

Very simplified:

```text
Python
→ easy scripting, AI, research

Kotlin
→ apps, backend, Android

TypeScript
→ web development

Zig
→ systems programming, control, performance
```

Different languages give humans different ways to express instructions.

For ZastAPI⚡, Zig is especially interesting because we want things like:

```text
speed
small binaries
explicit memory control
low-level access
cross-platform builds
few hidden layers
```

We will learn what those mean much later.

# 9. Source code is text

Important idea:

Your file:

```text
src/main.zig
```

is basically a text file.

Inside it:

```zig
pub fn main() void {
}
```

is text written according to Zig's rules.

So:

```text
main.zig
=
text file
+
Zig syntax
```

It becomes meaningful because the Zig tools know how to interpret that syntax.

---

# 10. File extension tells us the language

You have seen:

```text
main.zig
```

The ending:

```text
.zig
```

tells us:

> This file contains Zig source code.

Same pattern:

```text
hello.py     → Python
app.kt       → Kotlin
index.ts     → TypeScript
main.zig     → Zig
```

The extension helps tools know what kind of source code they are dealing with.

---

# 11. What if we make a mistake?

Suppose Zig expects something like:

```zig
const name = "Babar";
```

but we write:

```zig
const name "Babar";
```

We forgot:

```text
=
```

The compiler can inspect the source code and report that something is wrong.

Conceptually:

```text
Your Zig code
     ↓
Compiler checks it
     ↓
Something invalid
     ↓
Error message
```

Errors are not the computer "getting angry." 😄

They are useful messages telling us:

> I cannot understand or accept this code as written.

We'll learn how to read compiler errors carefully later.
